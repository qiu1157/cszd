# 充电站管理系统前端开发规范和要求

## 1. 目标

本规范用于统一充电站管理系统前端实现方式，保证后续页面开发在视觉风格、组件抽象、交互行为、代码组织、可维护性和移动端适配上保持一致。

本项目定位为：

- 企业内部后台系统
- PC 优先，手机端完整可操作
- 强调高密度业务信息展示
- 强调状态可视化、时间线可视化和表单录入效率

## 2. 技术栈要求

### 2.1 基础技术

- 框架：`Vue 3`
- 语言：`TypeScript`
- UI 组件库：`Element Plus`
- 路由：`Vue Router`
- 状态管理：`Pinia`
- 网络请求：`Axios`
- 构建工具：`Vite`
- 样式方案：`SCSS + CSS 变量`

### 2.2 统一要求

- 禁止在页面中直接写大段内联样式，主题变量除外。
- 禁止把接口请求逻辑直接堆在页面文件中。
- 禁止把业务枚举散落在多个页面内重复定义。
- 页面、组件、接口、状态、枚举、工具函数必须分层组织。

## 4. 页面设计基线

### 4.1 整体视觉方向

本系统建议采用“工业能源中控台”风格，而不是传统浅色办公后台：

- 主基调：深色石墨蓝 + 青绿能量色 + 琥珀强调色
- 关键词：稳定、专业、能源、调度、可视化、审计感
- 氛围：像运营控制台，而不是普通表单系统

### 4.2 页面层级

页面层级建议统一为：

1. 页面标题区
2. 筛选与操作区
3. 主内容区
4. 辅助信息区
5. 浮层区

### 4.3 视觉风格要求

- 卡片圆角保持克制，避免过于互联网营销风。
- 表格、筛选区、详情块的边界要清晰。
- 状态色要有统一语义，不允许同义不同色。
- 保留足够留白，但不做过度松散的布局。
- 时间线、状态标签、统计卡片需要具有明显识别性。

## 5. 设计 Token 规范

### 5.1 颜色

建议至少维护以下语义变量：

```css
--bg-page
--bg-panel
--bg-soft
--line-soft
--text-primary
--text-secondary
--text-muted
--brand-primary
--brand-accent
--success
--warning
--danger
--info
```

### 5.2 状态颜色统一

- 签合同：琥珀色
- 建设中：蓝色
- 运营中：绿色
- 运营异常：红橙色
- 停用：灰色
- 启用：绿色
- 已退出：灰红色

### 5.3 间距

统一采用 4 的倍数体系：

- `4 / 8 / 12 / 16 / 20 / 24 / 32 / 40`

推荐：

- 页面区块间距：`24`
- 卡片内边距：`20` 或 `24`
- 表单行距：`16`
- 移动端卡片内边距：`16`

### 5.4 字体

- 页面标题：`28-32px`
- 模块标题：`18-20px`
- 表格正文：`14px`
- 辅助说明：`12-13px`

要求：

- 字体层级必须清晰。
- 不同模块不得随意改字号。
- 数字统计建议使用更强识别度的数字字形。

## 6. 布局规范

### 6.1 主布局

- 左侧固定导航
- 顶部保留系统标题、当前角色、搜索入口、账号入口
- 主体内容采用最大宽度自适应布局

### 6.2 列表页

列表页统一包含：

- 页面标题
- 描述信息
- 筛选栏
- 操作按钮区
- 数据表格 / 卡片列表
- 分页区

### 6.3 详情页

详情页统一包含：

- 返回入口
- 标题区
- 状态概览
- 单页分区锚点导航
- 基础信息块
- 子业务块
- 历史时间线块

### 6.4 手机端

手机端统一原则：

- 左侧菜单改为抽屉式导航
- 列表表格需降级为卡片列表或紧凑表格
- 分区改为纵向堆叠
- 固定操作按钮需避免遮挡底部内容

## 7. 组件规范

### 7.1 组件拆分原则

- 页面组件负责组合，不负责复杂复用逻辑。
- 复用业务块必须提炼为业务组件。
- 通用空状态、加载态、状态标签、时间线条目、统计卡片要独立组件化。
- 表单弹窗和独立编辑页共享字段配置时，要抽为独立 schema 或 composable。

### 7.2 推荐业务组件

- `AppPageHeader`
- `MetricCard`
- `StatusTag`
- `FilterToolbar`
- `StationSummaryCard`
- `TimelinePanel`
- `TimelineEventItem`
- `SectionAnchorNav`
- `InfoGrid`
- `EmptyState`

### 7.3 表单组件要求

- 表单字段必须有清晰标签。
- 必填项需显式标识。
- 复杂表单需按逻辑分组。
- 状态切换、股权调整等高风险操作要有确认反馈。

## 8. 页面开发要求

### 8.1 登录页

- 登录页风格需与后台整体一致。
- 不要使用过度普通的白底登录框。
- 登录区要突出“能源管理系统”属性。
- 错误提示要明确。

### 8.2 首页

- 首页重点不是堆图表，而是让用户快速看懂系统运行概况。
- 统计卡片必须能一眼区分不同状态。
- 最近操作记录要可点击进入关联页面。
- 快捷入口要与实际高频动作一致。

### 8.3 充电站列表

- 强调查询效率。
- 状态、平台、联系人等信息密度要高但不拥挤。
- 列表行要能快速看出“站点当前状态”和“桩规模”。

### 8.4 充电站详情

- 页面必须突出站点身份、状态和基础信息。
- 单页分区要便于滚动定位。
- 充电桩、股东、时间线三个区域要层次清晰。
- 页面顶部建议有站点摘要卡。

### 8.5 股东管理

- 股东列表要体现“独立主档”概念。
- 股东详情页需要同时承载基础信息、关联站点、历史时间线。
- 默认展示全部站点事件，并支持按充电站筛选。

### 8.6 平台管理

- 平台页更偏字典管理，保持清晰、简洁。
- 不要过度复杂化。
- 页面需预留未来增加对接参数的扩展空间。

### 8.7 操作日志

- 日志页要体现“审计中心”气质。
- 时间、操作人、对象类型、变化摘要必须清晰。
- 展开详情时要能看到修改前后内容。

### 8.8 股权调整页

- 这是第一期最复杂的业务页之一。
- 需要强调总占比 `100%` 的规则提示。
- 多股东编辑要清晰、可控、可校验。
- 保存前后状态反馈必须明确。

## 9. 状态与反馈规范

### 9.1 加载态

- 列表加载使用骨架或表格 loading。
- 卡片加载使用骨架屏。
- 禁止整页纯文本“加载中”。

### 9.2 空状态

- 空状态必须给出下一步操作建议。
- 例如“暂无充电站，去新增一个站点”。

### 9.3 错误态

- 表单错误要定位到字段。
- 页面错误要提供重试入口。
- 网络异常要给出明确反馈。

### 9.4 成功反馈

- 保存成功使用轻提示 + 页面数据更新。
- 高风险动作可使用确认框。
- 不要所有操作都使用弹窗打断。

## 10. 表格规范

- 表格列宽要有明确优先级。
- 首列信息应优先展示核心识别字段。
- 状态列必须统一使用状态标签。
- 操作列按钮不宜过多，建议保留主操作 + 更多。
- 在手机端尽量降级为卡片，不强撑完整表格。

## 11. 时间线规范

- 时间线按倒序展示。
- 每条事件至少包括：时间、操作人、对象、事件摘要。
- 支持展开查看详情。
- 股权调整、状态变更、持股关系退出等关键事件要有高亮样式。

## 12. 路由与权限要求

- 路由必须与菜单权限绑定。
- 菜单隐藏不代表权限完成，接口层仍需鉴权。
- 系统管理员与业务管理员的页面入口要按角色控制。
- 页面内的按钮级权限也要控制。

## 13. 数据与接口约束

### 13.1 枚举统一管理

以下枚举必须集中管理：

- 充电站状态
- 充电桩状态
- 股东状态
- 持股关系状态
- 用户角色
- 日志对象类型

### 13.2 接口分层

- `api` 目录只负责请求。
- `store` 负责页面共享状态。
- `views` 不直接拼装复杂数据结构。
- 复杂数据转换应放在 `adapter` 或 `utils` 中。

## 14. 代码规范

### 14.1 命名

- 页面组件：`PascalCase`
- 组合式函数：`useXxx`
- Store：`useXxxStore`
- 样式类名：语义化命名

### 14.2 文件大小控制

- 单个页面文件过大时必须拆分子组件。
- 单文件超过 300 行时，优先检查是否需要抽离。
- 股权调整、时间线、详情头部等复杂区块必须拆分。

### 14.3 注释要求

- 关键业务规则要写“为什么”而不是“做什么”。
- 特别是持股总和校验、角色限制、状态变更规则等位置要有简明中文注释。

## 15. 性能与体验要求

- 避免重复请求相同字典数据。
- 平台字典、状态枚举等优先缓存。
- 列表查询要支持防抖。
- 大列表要考虑分页，不做整页一次性渲染。
- 时间线默认按分页或分段加载，避免无限堆积。

## 16. 安全要求

- 不在前端保存明文密码。
- 不把敏感信息输出到控制台。
- 权限按钮只作为体验层控制，不能替代后端鉴权。
- 重置密码、高风险状态切换等动作需有二次确认。

## 17. 原型到开发的落地要求

- 原型中的布局、信息层级、状态样式、时间线结构需尽量保留到开发阶段。
- Mock 数据字段命名应尽量贴近真实业务字段，避免后续重新理解。
- 原型中已经验证有效的分区结构、统计卡片和时间线交互，应优先进入正式实现。
- 如后续新增页面，必须遵循本规范中的布局、状态色、表单和时间线规则。
