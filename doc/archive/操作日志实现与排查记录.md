# 操作日志实现与排查记录（归档）

> 本文档归档统一操作日志（里程碑 G）的实现方式与开发过程中遇到的两次关键修复。
> 权威规范见 `doc/design/系统规格说明.md` §9.5，开发自检清单见 `doc/development/开发流程与规范.md`。

## 1. 实现概述

采用 **AOP + 注解** 方式统一记录操作日志，业务代码无侵入。

核心组件（包路径 `com.changsha.zhongdian.operationlog`）：

- 注解 `@LogOperation`：标记需记录日志的方法，支持 `targetType`、`operationType`、`targetIdSpEL`、`targetNameSpEL`、`stationIdSpEL`、`remarkSpEL`、`captureBeforeState`。
- 切面 `OperationLogAspect`：拦截带注解方法，用 SpEL 从参数/返回值提取日志信息，从请求上下文取当前登录用户，调用 `OperationLogService` 落库。
- 实体 `OperationLog`：落库到 `biz_operation_log` 表。
- 枚举 `OperationType`（CREATE/UPDATE/DELETE/EXIT）、`OperationTargetType`（STATION/PILE/SHAREHOLDER/SHAREHOLDING）。

关键约束：

- 所有 CommandService 写方法必须返回**实体对象**（不能返回 Long ID），以便 SpEL 通过 `#result.xxx` 提取属性。
- Controller 层调用后通过 `.getId()` 提取 ID 返回前端，不直接返回实体。

## 2. 修复记录一：Repository JPQL 字段引用错误

**现象**：应用启动报 `UnsatisfiedDependencyException` → `UnknownPathException: Could not resolve attribute 'shareholder' of 'Shareholding'`。

**根因**：`Shareholding` 实体采用解耦设计，只存 `shareholderId` / `stationId` 主键字段，无 `@ManyToOne` 关联；而 JPQL 误写了 `sh.shareholder.id`、`sh.station.id`。

**修复**：改为 `sh.shareholderId`、`sh.stationId`；枚举比较改用完整枚举路径而非字符串字面量；正确使用 `CAST` 处理字符串与数值类型转换。

**防护**：新增 `OperationLogRepositoryTest`、`OperationLogQueryServiceTest` 单元测试。

## 3. 修复记录二：事务传播导致日志丢失

**现象**：修改充电站地址后，`biz_operation_log` 无对应记录。

**根因**：`OperationLogService.log` 使用 `@Transactional(propagation = Propagation.REQUIRED)`，与主业务事务耦合——主业务异常时日志一起回滚，或日志保存失败拖累主业务。

**修复**：改为 `@Transactional(propagation = Propagation.REQUIRES_NEW)`，操作日志写入独立事务，与主业务解耦。

## 4. 诊断清单（日志未记录时）

按顺序排查：

1. **数据库层**：查询 `biz_operation_log` 是否有目标记录；完全没有 → AOP 未生效。
2. **AOP 层**：确认 `OperationLogAspect` 有 `@Aspect` + `@Component`，主类有 `@SpringBootApplication`。
3. **认证层**：确认 `AuthInterceptor` 正确写入当前用户到请求属性。
4. **前状态捕获**：确认写方法内调用 `BeforeStateHolder.set(...)` 且未被提前 clear。
5. **事务层**：确认 `OperationLogService.log` 为 `REQUIRES_NEW`（见第 3 节）。
6. **前端层**：确认 `/api/operation-logs/timeline/station/{id}` 返回数据、组件正确渲染。

诊断 SQL 见 `doc/archive/操作日志诊断SQL.sql`。
